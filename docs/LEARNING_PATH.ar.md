## 1. أساسيات Terraform 101 ودورة حياة البنية التحتية

تعد البنية التحتية كتعليمات برمجية (Infrastructure as Code - IaC) الأساس الذي تعتمد عليه كبرى المؤسسات التقنية لإدارة السحابة بطريقة مؤتمتة وموثوقة.

### ما هي البنية التحتية ككود (IaC)؟
في السابق، كان مهندسو الأنظمة ينشئون الموارد يدوياً من خلال لوحة تحكم AWS بالضغط على الأزرار ("ClickOps").  
**عيوب الطريقة اليدوية (ClickOps)**:
- نسبة خطأ بشري مرتفعة جداً قد تؤدي لتوقف الأنظمة الحساسة.
- انعدام التوثيق وسجل التعديلات (Audit Trail) لمعرفة من قام بالتغيير.
- حدوث انحراف في الإعدادات (Configuration Drift) بين بيئة الاختبار وبيئة الإنتاج.

**الحل: استخدام Terraform (IaC)**  
تستخدم أداة Terraform لغة التصريح (HCL - HashiCorp Configuration Language) لتحديد الحالة النهائية المطلوبة للبنية التحتية. تقوم الأداة بحساب الفارق بين الواقع والكود وتطبيق التغييرات بأمان.

### اللبنات الأساسية لـ Terraform

| المفهوم | المعنى والوظيفة | التشبيه الواقعي |
| :--- | :--- | :--- |
| **المزوّد (Provider)** (`providers.tf`) | إضافة برمجية تترجم أوامر Terraform إلى نداءات لواجهات برمجة تطبيقات AWS (API). | برنامج تشغيل الطابعة أو المترجم الفوري. |
| **المورد (Resource)** (`resource "aws_vpc"`) | المكون الفعلي المراد إنشاؤه في السحابة (مثل شبكة، خادم، قاعدة بيانات). | حجر البناء أو الغرفة في المبنى. |
| **المتغيرات (Variables)** (`variables.tf`) | مدخلات ديناميكية تجعل الكود قابلاً لإعادة الاستخدام في بيئات مختلفة. | معلمات الدوال البرمجية (Parameters). |
| **المخرجات (Outputs)** (`outputs.tf`) | معلومات يتم تصديرها بعد اكتمال البناء (مثل عنوان العنقود، معرّف الشبكة). | القيمة المرجعة من الدالة البرمجية (Return Value). |
| **الوحدة (Module)** (`modules/vpc`) | مجلد يحتوي على موارد مترابطة يتم التعامل معها كوحدة واحدة مستقلة. | فئة برمجية (Class) أو مكتبة قابلة للاستدعاء. |
| **ملف الحالة (State File)** (`terraform.tfstate`) | "عقل" Terraform الذي يخزن الربط بين الأكواد والمعرّفات الفعلية داخل AWS. | المخطط الهندسي الحقيقي للبناء المكتمل على أرض الواقع. |

### المراحل الخمس لدورة حياة Terraform

```text
 [1. terraform fmt]      ──► تنسيق الكود والتأكد من مطابقة المعايير الجمالية
         │
         ▼
 [2. terraform init]     ──► تنزيل إضافات المزودات وتهيئة التخزين السحابي للحالة
         │
         ▼
 [3. terraform validate] ──► فحص سلامة بناء الجملة وأنواع المتغيرات
         │
         ▼
 [4. terraform plan]     ──► استرجاع الحالة الحالية وحساب الفارق الإنشائي بدقة
         │
         ▼
 [5. terraform apply]    ──► إرسال الأوامر المعتمدة إلى AWS لإنشاء الموارد الفعلية
```

## 2. معمارية "التطبيق بضغطة واحدة" (One-Go Apply)

### معضلة "البيضة والدجاجة" في إدارة Kubernetes بواسطة IaC
تفشل الكثير من مشاريع EKS المبنية بـ Terraform عند تشغيلها للمرة الأولى في حساب AWS جديد.  
**السبب**: محاولة مزودات Kubernetes و Helm الاتصال بالعنقود أثناء مرحلة التخطيط المبدئية (`terraform plan`) قبل أن يكون العنقود أو شهاداته الأمنية قد أُنشئت بالفعل.

### كيف يضمن هذا المشروع النجاح بنسبة 100% من المحاولة الأولى؟
1. **الاعتماد على إضافات AWS الرسمية المباشرة**: نستخدم مورد `aws_eks_addon` لإدارة مكونات (`vpc-cni`, `kube-proxy`, `coredns`) بدلاً من تثبيت Helm أثناء البناء الأولي.
2. **شجرة الاعتماديات الصريحة**:
   ```hcl
   module "eks" {
     source = "./modules/eks"
     depends_on = [module.vpc, module.iam]
   }
   ```
3. **المصادقة الديناميكية**: في `providers.tf`، يتم الحصول على رموز الدخول المميزة dynamically باستخدام `aws eks get-token` لتفادي انتهاء صلاحية الرموز أثناء عمليات النشر الطويلة.

## 4. الوحدة الأولى: طبقة الشبكات (VPC والشبكات الفرعية)

موجودة في المجلد `modules/vpc`:
- **نطاق العناوين (CIDR)**: `10.0.0.0/16` (يوفر 65,536 عنوان IP خاص).
- **التوزيع الجغرافي العالي**: مقسمة عبر 3 مناطق توافر (`ap-south-1a`, `ap-south-1b`, `ap-south-1c`).
- **الشبكات العامة (Public Subnets)**:
  - تستضيف بوابة الإنترنت وبوابات NAT وموازنات الأحمال الخارجية.
  - مميزة بالوسم `kubernetes.io/role/elb = 1` ليتعرف عليها AWS Load Balancer Controller تلقائياً.
- **الشبكات الخاصة (Private Subnets)**:
  - مخصصة حصرياً لخوادم Kubernetes وحاويات التطبيقات بدون أي عناوين IP عامة.
  - جميع الاتصالات الصادرة بالإنترنت تمر حصراً وبأمان عبر بوابة NAT.
  - مميزة بالوسم `kubernetes.io/role/internal-elb = 1` لموازنات الأحمال الداخلية بين الخدمات المصغرة.
- **التحكم في التكلفة مقابل التوفر العالي**:
  - `enable_ha_nat_gateway = false`: بوابة NAT واحدة لبيئات التطوير لتوفير التكاليف.
  - `enable_ha_nat_gateway = true`: بوابة NAT مستقلة في كل منطقة توافر لبيئات الإنتاج الصارمة.

## 5. الوحدة الثانية: طبقة الهوية والأمان (IAM و IRSA)

موجودة في المجلد `modules/iam`:
- **مبدأ الامتيازات الأقل (Least Privilege)**: فصل كامل بين أدوار IAM الممنوحة للوحة تحكم العنقود وتلك الممنوحة لعقد العمل.
- **إدارة الخوادم الآمنة عبر AWS Systems Manager**:
  - إرفاق سياسة `AmazonSSMManagedInstanceCore`.
  - يتيح ذلك لمهندسي التشغيل الدخول إلى العقد واستكشاف الأخطاء عبر جلسات مشفرة وموثقة بالكامل دون الحاجة لمفاتيح SSH ودون فتح المنفذ 22 على الإنترنت.
- **أدوار IAM لحسابات خدمة Kubernetes (IRSA)**:
  - ربط مزود الهوية OIDC بالعنقود.
  - يتيح ذلك لكل تطبيق (Pod) الحصول على صلاحيات AWS محددة جداً ومؤقتة عبر خدمة STS (`AssumeRoleWithWebIdentity`) بدلاً من منح الخادم صلاحيات عامة واسعة وخطيرة.

## 6. الوحدة الثالثة: الحوسبة وتنسيق الحاويات (EKS 1.36)

موجودة في المجلد `modules/eks`:
- **لوحة التحكم**: تعمل على أحدث إصدارات **Kubernetes 1.36**.
- **المراقبة والسجلات**: تصدير كافة أنواع السجلات الخمسة (`api`, `audit`, `authenticator`, `controllerManager`, `scheduler`) إلى Amazon CloudWatch.
- **تشفير الأسرار (Envelope Encryption)**: تشفير أسرار Kubernetes المحفوظة في قاعدة بيانات `etcd` باستخدام مفتاح تشفير مدار من العميل في AWS KMS.
- **مجموعات العقد المدارة (Managed Node Groups)**:
  - خوادم `t3.medium` قابلة للتوسع.
  - ترقيات بدون توقف للخدمة (`max_unavailable = 1`).
  - حماية مشددة من هجمات SSRF بفرض بروتوكول **IMDSv2** الصارم.

## 7. الوحدة الرابعة: خط أنابيب GitOps CI/CD وبوابات الجودة

يفرض المشروع مراجعات وفحوصات مؤتمتة قبل السماح لأي كود بلمس سحابة AWS:

| نقطة الفحص | مسار العمل | الأداة / الأمر | الغرض والوظيفة |
| :--- | :--- | :--- | :--- |
| **نقطة 1** | `terraform-ci.yml` | `terraform fmt -check -diff` | فرض معايير التنسيق البرمجي الموحدة |
| **نقطة 2** | `terraform-ci.yml` | فاحص Trivy الأمني | كشف الثغرات الأمنية والأخطاء المعمارية في الكود |
| **نقطة 3** | `terraform-ci.yml` | `terraform validate` وتلخيص PR | التحقق من صحة المخططات ونشر النتائج في تعليق تلقائي |
| **نقطة 4** | `terraform-apply.yml` | تشغيل يدوي مشروط (`APPLY`) | حظر النشر التلقائي واشتراط التأكيد البشري الصريح |
| **الإزالة الآمنة** | `terraform-destroy.yml` | كلمة تأكيد وبوابة بيئة معتمدة | اشتراط كتابة `DESTROY-PRODUCTION` وموافقة المراجعين |

## 8. أهم 17 سؤالاً وجواباً في مقابلات مهندسي DevOps و SRE

### س1: لماذا يجب وضع خوادم Kubernetes داخل شبكات فرعية خاصة حصراً؟
**الجواب**: لحمايتها تماماً من التعرض المباشر للإنترنت العام، مما يمنع هجمات المسح الشبكي، ومحاولات الاختراق بالقوة الغاشمة (Brute Force)، وثغرات استغلال المنافذ المفتوحة.

### س2: كيف يعمل محول الشبكات AWS VPC CNI ولماذا يحتاج إلى نطاق CIDR واسع؟
**الجواب**: على عكس الشبكات المتراكبة (Overlay) التي تضيف عبئاً على الحزم، يقوم AWS VPC CNI بتعيين عناوين IP فرعية حقيقية من الشبكة الخاصة للحاويات مباشرة، مما يمنحها سرعة الأسلاك الفيزيائية للشبكة، لكن ذلك يستهلك عناوين IP حقيقية بكثرة مما يستلزم نطاقاً واسعاً مثل `/16`.

### س3: ما هي تقنية IRSA ولماذا هي أفضل من ملفات تعريف خوادم EC2؟
**الجواب**: تسمح IRSA لكل حاوية (Pod) بالحصول على دور IAM مستقل وخاص بها تماماً عبر OIDC و STS. بدونها، تضطر جميع الحاويات الموجودة على نفس الخادم لمشاركة نفس الصلاحيات الممنوحة للخادم، مما ينتهك مبدأ الامتيازات الأقل.

### س4: لماذا يُعد بروتوكول IMDSv2 إلزامياً على عقد EKS؟
**الجواب**: لمنع هجمات تزوير الطلبات من جانب الخادم (SSRF). في الإصدار القديم IMDSv1، كان بإمكان المهاجم سرقة بيانات اعتماد خادم EC2 عبر طلب `GET` بسيط. بينما يفرض IMDSv2 جلسة مصادقة تبدأ بطلب `PUT` مشفر برمز مميز محمي.

### س5: ما فائدة وسوم الشبكات `kubernetes.io/role/elb` و `internal-elb`؟
**الجواب**: يستعلم متحكم AWS Load Balancer Controller عن هذه الوسوم تلقائياً لمعرفة الشبكات المناسبة لنشر موازنات الأحمال؛ الوسم الأول للموازنات العامة المواجهة للإنترنت، والوسم الثاني للموازنات الداخلية الخاصة.

### س6: كيف تحقق ترقية العقد دون أي انقطاع في الخدمة (Zero-Downtime Rolling Upgrade)؟
**الجواب**: باستخدام سياسة `max_unavailable = 1`؛ حيث تقوم AWS بتشغيل خادم جديد بالإصدار المحدث، ثم تفريغ الحاويات تدريجياً من الخادم القديم باحترام قواعد PDB، والانتظار حتى تصبح الحاويات جاهزة تماماً قبل إنهاء الخادم القديم.

### س7: ما هو التشفير المغلف (Envelope Encryption) لأسرار EKS؟
**الجواب**: يتم تشفير أسرار Kubernetes المخزنة في `etcd` باستخدام مفتاح تشفير بيانات فريد (DEK)، ويتم تشفير هذا المفتاح نفسه باستخدام مفتاح رئيسي مدار من العميل في خدمة AWS KMS.

### س8: لماذا يجب إغلاق منفذ SSH رقم 22 تماماً على خوادم الإنتاج؟
**الجواب**: لأن إدارة المفاتيح وتوزيعها ينطوي على مخاطر أمنية عالية. بدلاً من ذلك، نستخدم AWS Systems Manager (SSM) Session Manager للدخول الآمن عبر واجهة AWS مع توثيق وتسجيل كامل لكل أمر في CloudTrail.

### س9: لماذا يُعتبر الجمع بين S3 و DynamoDB إلزامياً لملف حالة Terraform؟
**الجواب**: يوفر S3 تخزيناً سحابياً مشفراً ومحفوظ الإصدارات لملف الحالة، بينما يوفر DynamoDB خاصية القفل الموزع (Distributed Locking) عبر سمة `LockID` لمنع التعديلات المتزامنة التي قد تؤدي لتلف ملف الحالة (Race Conditions).

### س10: ما الفرق بين السعات On-Demand و Spot في عقد الحوسبة؟
**الجواب**: توفر On-Demand سعة مضمونة للأحمال الحساسة والحرجة، بينما توفر Spot خصومات تصل إلى 90% على السعات الفائضة في مراكز بيانات AWS مع إشعار استرداد مدته دقيقتان. المعمارية المثالية تدمج بينهما.

### س11: كيف تمنع Terraform من التعارض مع التوسع التلقائي للـ Kubernetes Autoscaler؟
**الجواب**: بإضافة الكتلة التالية إلى مورد العقد:
```hcl
lifecycle {
  ignore_changes = [scaling_config[0].desired_size]
}
```
حتى لا تعيد Terraform تقليص العقد عند تغير حركة المرور.

### س12: ما الفرق بين بوابة NAT مفردة وبوابات NAT متعددة المناطق؟
**الجواب**: بوابة NAT المفردة توفر قرابة 64 دولاراً شهرياً لكنها تشكل نقطة فشل وحيدة (Single Point of Failure). في المقابل، تضمن البوابات المتعددة استمرارية العمل حتى في حال توقف منطقة توافر كاملة في AWS.

### س13: لماذا نحدد صراحة `depends_on = [module.vpc, module.iam]` في العنقود؟
**الجواب**: لأن واجهات برمجة تطبيقات EKS تتطلب أن تكون الشبكات وجداول التوجيه وأدوار IAM نشطة ومفعلة بالكامل قبل البدء في إنشاء لوحة التحكم لتفادي أخطاء المهلة الزمنية.

### س14: ما الفرق التقني بين `terraform validate` و `terraform plan`؟
**الجواب**: يفحص `validate` قواعد بناء الجملة والاتساق الداخلي محلياً دون أي اتصال بالسحابة، بينما يتصل `plan` بمزود السحابة لقراءة الواقع الفعلي ومقارنته بالكود لحساب التغييرات بدقة.

### س15: ما هو الترتيب العكسي الذي تتبعه Terraform أثناء حذف الموارد؟
**الجواب**: تحذف أولاً الإضافات ومجموعات العقد، ثم لوحة تحكم EKS ومفاتيح KMS، ثم أدوار IAM وبوابات NAT وعناوين IP المرنة، ثم الشبكات الفرعية وجداول التوجيه، وأخيراً شبكة VPC.

### س16: كيف يتم تمرير المتغيرات ومخرجات الخطوات بين مهام مختلفة في GitHub Actions؟
**الجواب**: سياق `steps` معزول داخل كل مهمة (Job) على حدة. لتمرير البيانات، يجب على المهمة الأولى تعريف مخرجات رسمية (`outputs`)، بينما تعلن المهمة التالية اعتمادها عليها بواسطة `needs` وتقرأ القيمة عبر سياق `needs`.

### س17: ماذا يحدث إذا نُفذ أمر `terraform apply` على بيئة CI مؤقتة بدون تخزين سحابي للحالة (Remote Backend)؟
**الجواب**: بمجرد انتهاء الخادم المؤقت، يُحذف ملف `terraform.tfstate` نهائياً. وتظل موارد السحابة تعمل باسم "البنية التحتية الشبحية" (Ghost Infrastructure) وتستمر التكاليف بالتراكم دون علم الفريق، وعند محاولة الحذف لاحقاً يبلغك Terraform بأنه تم حذف 0 موارد. الحل هو استخدام S3 مع DynamoDB دائماً، وتوفير سكربتات تدمير شاملة تعتمد على الوسوم المباشرة في السحابة.

## 9. الأوامر التطبيقية والتحقق العملي (التشغيل الآلي والإزالة الشاملة)

### 1. التهيئة التلقائية والتخطيط محلياً
```bash
# التهيئة التلقائية لمستودع S3 وقفل DynamoDB (بدون أي عمل يدوي)
chmod +x scripts/*.sh
./scripts/auto-bootstrap.sh

# تنسيق الكود
terraform fmt -recursive

# تهيئة المزودات والاتصال بالتخزين السحابي للحالة
terraform init

# فحص صحة القواعد
terraform validate

# مراجعة خطة النشر
terraform plan -out=tfplan
```

### 2. النشر السحابي الكامل بضغطة واحدة
```bash
terraform apply tfplan
```

### 3. الاتصال بالعنقود والتحقق من صحة العقد
```bash
# تحديث ملف إعدادات kubectl محلياً
aws eks update-kubeconfig --region ap-south-1 --name eks-production-cluster

# التحقق من حالة وجاهزية عقد العمل
kubectl get nodes -o wide

# التحقق من تشغيل حاويات النظام الأساسية
kubectl get pods -n kube-system
```

### 4. الإزالة والتدمير الشامل (Total Wipeout)
```bash
# الخيار أ: الحذف القياسي بـ Terraform (يحتفظ بملف الحالة في S3)
terraform destroy -auto-approve

# الخيار ب: التدمير الشامل الآمن (يحذف العنقود، الشبكات، أدوار IAM، وكذلك حاوية S3 وجدول DynamoDB تماماً)
./scripts/teardown.sh
```

## 10. حل المشكلات الميدانية وتجارب بيئات الإنتاج الحقيقية

### ⚠️ دراسة الحالة 1: خطأ نطاق السياق عبر مهام GitHub Actions

* **نص الخطأ**:
  ```text
  Context access might be invalid: fmt @[.github/workflows/terraform-ci.yml:L100]
  ```
* **السبب الجذري**:
  تم تقسيم سير العمل إلى 3 مهام منفصلة: فحص التنسيق، الفحص الأمني، والتحقق الإنشائي. حاول السكربت في المهمة الثالثة قراءة `${{ steps.fmt.outcome }}` مباشرة، لكن في GitHub Actions يكون سياق `steps` محصوراً في مهمته فقط مما أعطى قيمة فارغة `null`.
* **الحل المعماري للإنتاج**:
  1. تصدير المخرج صراحة في مهمة فحص التنسيق:
     ```yaml
     code-quality:
       outputs:
         fmt_outcome: ${{ steps.fmt.outcome }}
     ```
  2. ربط الاعتمادية في المهمة المستفيدة:
     ```yaml
     terraform-plan:
       needs: [code-quality, security-scan]
     ```
  3. قراءة القيمة عبر سياق `needs`:
     ```yaml
     - 🖌 **Format**: `${{ needs.code-quality.outputs.fmt_outcome || 'Passed' }}`
     ```

### 🚨 دراسة الحالة 2: معضلة الخوادم المؤقتة و"العناقيد الشبحية" الضائعة

* **سيناريو الحادثة**:
  عند دمج كود جديد، قام خط الأنابيب ببناء العنقود وشبكاته بالكامل على خادم GitHub Actions بنجاح. لكن نظراً لأن إعداد التخزين السحابي البعيد في `versions.tf` كان معطلاً، حُفظ ملف الحالة على القرص المؤقت للخادم والذي دُمّر فور اكتمال المهمة.
* **الأثر على الأعمال والتكاليف**:
  عند محاولة حذف المشروع لاحقاً، قرأ Terraform حالة فارغة وأعلن حذف 0 موارد، وظل عنقود EKS وبوابة NAT يعملان في الخفاء مولدين تكاليف تتجاوز 100 دولار شهرياً دون علم أحد.
* **الحلول المعمارية المتخذة**:
  1. **حظر النشر التلقائي**: جعل أمر `apply` مشروطاً دائماً بتأكيد كتابي وموافقة بشرية عبر `workflow_dispatch`.
  2. **سكربت التهيئة الذاتية (`scripts/auto-bootstrap.sh`)**: التحقق الآلي من وجود S3 و DynamoDB وإنشائهما فوراً قبل أي تشغيل لـ `terraform init`.
  3. **سكربت التدمير الشامل المضمون (`scripts/teardown.sh`)**: سكربت ذكي يستعلم واجهات برمجة تطبيقات AWS مباشرة بناءً على وسوم المشروع، ويحذف كافة الموارد بترتيب الاعتمادية العكسي، ويختم بتفريغ وحذف حاوية S3 وجدول DynamoDB ليصبح الحساب نظيفاً تماماً بتكلفة صفرية مؤكدة.
